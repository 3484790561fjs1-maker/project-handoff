# 这套 Skill 的维护背景

## 用户要解决什么

用户在公司和家里两台电脑轮流开发。希望通过 GitHub 同步代码、固定规则、架构、决策和当前进展，新电脑上的新对话能接着做。既支持小项目，也支持多模块工具箱；优先提高交付速度并控制总 token 消耗。说明要简洁，提示词能直接复制。

新项目流程：需求对齐 → 按用户专属 UI 规则选方案 → 计划与开发 → 验证 → 收工推送 → 换电脑开工。用户尚未提供 UI 规则；工具箱是使用示例，没有在本仓库实现业务应用。

## 代码结构与职责

- `skills/project-dev/`：统一入口；`references/start.md` 负责创建，`develop.md` 负责实施与集成，`parallel.md` 负责并行，`sync.md` 负责多任务交接。`assets/` 保存业务项目配置与任务模板。
- `skills/project-handoff/`：原有单项目交接组件，维护规则、架构、进展、决策和 Git 同步。`project-dev` 在它之上汇总多任务。
- `docs/project-dev-使用说明.md`：面向使用者的简明实操指南。
- `tests/verify_project_dev_flow.py`：临时本地 Git 流程演练，不代表真实 AI 或双机验证。
- `AGENTS.md`、本文件与 `docs/STATUS.md`：用于继续维护本套装。`.project-handoff.json` 登记源码仓库的交接入口。

## 已选择的方案与原因

1. **一个入口，默认直接开发。** 任务有依赖时集中做；只有接口确定、工作量足够且文件职责可分开时才并行，最多两个同时编码的执行者，主对话也计入，减少分工和重复上下文的成本。
2. **并行必须隔离。** 各任务使用独立 Worktree、分支和写入范围。主控负责公共接口、依赖和总进展；无法验证隔离时采用单路。
3. **业务新项目的主控交接目标固定为 `dev/work`，稳定内容放 `main`。** 初始 main 的入口也要指向交接分支，避免新电脑克隆后找不到最新进展。已有项目沿用自身约定。
4. **收工保存各任务，再汇总主控。** 先停止写入，逐一保存与推送相关分支并核验远端，最后同步总进展。未完成功能可按 WIP 交接，不为收工强行合并稳定主线。
5. **按需接入 Superpowers。** 本套装没有包含或安装它；可用时使用原版需求对齐等能力，不可用时明确使用基础流程。UI 沿用用户另行提供的规则。
6. **Git 同步持久资料。** 不迁移聊天、运行中的代理、本机依赖、凭据和私有数据库。不承诺固定提速或 token 节省比例。

## 继续改进时

先让用户提供具体问题：用了什么提示词、期望结果、实际结果。核对相关源码后，只修正受影响流程，维护相应文档并做必要验证；不要从头重新选型或重建整套 Skill。

源码更新、GitHub 推送、本机 Skill 安装是三个独立步骤，分别报告结果。若要带着新版本换电脑，在另一台电脑更新安装；仅拉取业务项目不会更新全局 Skill。
