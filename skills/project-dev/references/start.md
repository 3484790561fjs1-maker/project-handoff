# 创建与接入项目

## 先确认范围

当前目录必须是用户的业务项目。空目录可以按创建项目要求初始化；已有项目先读代码和规则，再增量接入。不能把通用 Skill 源码仓库当成要开发的业务项目。

先理解用户、核心用途、首版范围、平台和验收标准。能从已有资料确认的事实自行读取；只问会改变设计的缺失信息。技术栈沿用已选方案，或给出简短建议。用户只是咨询流程时，不创建业务文件。

## 需求、UI 与计划

1. 可用时接入 Superpowers 的需求对齐与计划能力。否则直接完成下面的基础流程，说明没有调用原插件。
2. 对新项目将已确认的目标、首版功能、范围边界和验收条件写入需求设计文档。未确认项保留为待定，不当作用户同意。
3. 有界面的项目按用户专属 UI 规则提供可选择的方案，保存方案与最终选择。未提供专属规则时仅就缺失的 UI 输入询问或记录待提供，不自创一套替代；纯后端任务或用户要求跳过 UI 时不设此阶段。原型不标为成品。
4. UI 选择和关键设计确认后更新设计，再生成当前阶段实施计划。计划包含能独立验收的功能、依赖、相关位置与验证方法，不预写大量完整实现代码，也不为未来每个小步骤复制背景。
5. 多工具项目先确定接入接口、共享 UI、依赖策略和模块边界，完成公共骨架和一个可用示范模块后再扩展。大项目不要求一次设计所有未来工具。

用户已确认的需求或阶段不反复询问。只在真正影响产品方向的选择处等待决定，不在每个实施任务之间请求继续。

## 初始化项目约定

可用时调用 `project-handoff` 的初始化，补齐项目规则、架构、进展、重要决策和环境说明。保留其 `.project-handoff.json` 作为远端与主控交接分支的唯一配置；并行工作者不得为自己的分支改写这个共享目标。

按实际项目采用 [../assets/project-dev.json](../assets/project-dev.json)。设置的文档路径均为项目内部相对路径，校验 JSON 版本和路径，不跟随越界路径。新项目可用 `docs/REQUIREMENTS.md`、`docs/PLAN.md`；已有设计计划文档则指向已有位置。任务清单只在需要多任务协调时创建。

将 [../assets/AGENTS.fragment.md](../assets/AGENTS.fragment.md) 的受管理片段合并到 `AGENTS.md`，保留用户其他内容；重复初始化只更新该段，损坏或多段标记先核实。配置未知值写 `null`，不要写虚构的仓库、命令、文件路径或组件安装状态。

没有 `project-handoff` 时最少补齐 `AGENTS.md`、README、当前状态和按需架构/决策文档；同步操作遵循 sync。不要为了采用此技能迁移整套既有文档。

## GitHub 与分支

用户要求上传或创建仓库时，核对账号、仓库归属和目标。个人新项目未指定可见性时使用 Private；已有远端不擅自更换。认证通过当前电脑已有工具或正规登录流程解决，不让用户贴令牌。

新项目默认使用 `main` 保存已验收内容，使用固定的 `dev/work` 作为主控开发与交接分支，独立工作者另外使用功能分支。阶段完成后继续复用 `dev/work`，不每天更换主控交接目标。已有项目沿用其明确约定，不擅自改分支体系。

首次建立仓库时，在将要保存到 main 的初始化配置中写明主控目标 `dev/work`，保存已确认的公共基准，再创建该分支；用户已要求上传时，两个分支均推送并核验。这样另一台电脑第一次克隆 main，也能从配置定位最新交接分支。不是让 project-handoff 在初始化尚未完成时按目标配置切走分支；两者建立并核对后才执行交接。

如果既有项目的主控目标发生已授权变更，要同时更新新电脑能读取的仓库入口，或在首次克隆指令中明确目标分支；不能只在新功能分支里改配置而让默认分支继续指向旧目标。入口未同步时必须在回报中给出接手所需的明确分支。

派发任务前先保存已确认的公共基准提交，未提交文件不会自然出现在另一 Worktree。阶段没完成也可以在对应开发分支交接，不强行为收工合并到 main。

README 写实际运行时版本、锁文件、安装/启动/验证命令、环境变量名及本地服务要求。真实配置值、本机依赖、私有数据不随 Git 分发。

## 停留位置

若本轮要求只对齐需求或选 UI，到相应结果为止。若要求完整开发，在必要的产品选择得到确认后继续已授权实施。结束时给出已完成阶段、所用组件、仍待决定项和下一步，不把新建文档说成项目已实现。
