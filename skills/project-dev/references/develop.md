# 实施与交付

## 恢复本轮位置

读取适用规则和当前状态，再按需查需求、计划、架构或任务记录。检查当前分支、工作区与近期提交，避免重新实现已完成内容。新聊天或压缩后的上下文依赖受 Git 管理的项目资料，不依赖其他电脑聊天记录。

开工同步是显式操作；用户要求“开工后继续”时先按 sync 同步，成功且环境满足任务才实施。普通开发指令不自动拉取、推送或创建仓库。

## 自动选择执行方式

默认主对话直接开发，同一功能的多个小改合在一次实施中。仅当以下条件全部成立时，读取 parallel 并并行：

- 有至少两项当前就能开始的任务，互相不等待结果；
- 接口和共享基础已确定，写入范围能清楚分开；
- 每项都有足够工作量和独立验收条件，值得承担上下文与集成成本；
- 可用执行能力能把各任务绑定到独立 Worktree 和分支。

项目大不自动代表需要并行。共享框架、接口重设计、迁移、跨模块重构通常集中实施。一次文案修正或零散小改不派出新工作者。为节省消耗，可保留同一工作者修复自己的任务，不为每个返工重建全新上下文。

用户偏好快速且少 token：默认不选择每个微任务都新开实现者与审查者的模式。如果采用已安装 Superpowers，本流程明确选择直接执行作为默认实施偏好；只有满足上述条件才安排独立任务并行。

## 反馈、验证与文档

采用当前任务需要的测试、构建和实际操作验证；明确验收失败的原因。可以由确定性工具完成的检查直接运行工具，不反复开启 AI 解释同一日志。变更后做针对性验证，功能或批次集成后检查组合行为；没有新变化或未解决疑点时不重复跑同一套完整检查。

按完整功能或当前阶段汇总审查。涉及公共接口、数据迁移或其他重要风险时，在对应位置增加审查。自检不能冒充独立审查；无可用审查者时如实说明，仍完成可以执行的验证。不为节省 token 跳过明确要求的验收。

仅更新因改动会过时的文档：结构变了改架构，重要选择改决策，环境命令变了改 README，阶段状态改当前进展。同一轮不维护多份重复总进展。

任务做到一半时记录当前实现、相关位置、已验证/未验证、阻塞和下一步。进展保持可快速接手的当前快照，避免追加完整聊天与日志。

## 集成、版本与提交边界

普通开发不默认为用户合并、推送或发布。“验收并合并”时核对具体来源和目标分支，审查实际 diff、接口兼容与未合入依赖，解决已授权范围内的问题并在集成结果上验证。只将通过验收的任务合入稳定分支；未完成任务留在自己的功能分支。

遵循既有 PR 流程。新个人项目可每个完整功能或独立模块一个 PR；同一阶段的细碎调整可合在一个交付单元，不为每行改动制造 PR。工作者默认只产出任务提交，主控统一执行远端操作和合并。

用户要求发布某版本时，更新变更记录，核对目标提交，再创建新标签/Release；已有同名标签不覆盖。阶段提交记录与验收版本不是同一件事。回退优先用可追踪的新提交或 revert，不重置强推稳定主线；部署与数据恢复需按实际目标另行处理。

完成回报简短给出：本次功能、实际验证、当前分支/提交、未完成事项。跨电脑前转入收工同步，不能把本地开发完成当作已经上传。
