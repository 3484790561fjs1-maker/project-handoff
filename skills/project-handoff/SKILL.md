# 项目交接

用 Git 同步代码和仓库内的项目上下文，让另一个电脑上的新会话能接手。默认跟随用户语言回复，中文项目使用中文交接文档。

## 选择本次操作

- **初始化交接／补齐交接配置**：读取 [references/setup.md](references/setup.md)，按真实项目合并模板。初始化不默认创建 GitHub 仓库、提交或推送，除非用户同时要求。
- **开工同步／换电脑继续**：读取 [references/sync.md](references/sync.md) 的“开工同步”。如果尚未克隆，先核实用户提供的仓库和目标路径；克隆后再读取项目规则。未给具体开发任务时，同步后输出接手摘要。
- **收工同步／下次接着做**：读取 [references/sync.md](references/sync.md) 的“收工同步”。收工同步包含对已核实的项目远端进行相关提交和推送；“仅更新文档”“暂不推送”等更具体要求优先。
- **只检查配置**：核对下面的入口和本地 Git 状态，报告缺项。用户限制为只读时不修改、拉取、提交或推送。

用户只说“同步”，且无法从上下文判断开工还是收工时，先只读检查，再问一个简短问题；不猜测推送范围。

## 项目入口

1. 确认用户实际工作的项目根目录；不要把技能仓库、父目录或其他项目当作业务项目。
2. 读取当前适用的 `AGENTS.md`（含目录级规则）和 `.project-handoff.json`，再按配置读取项目说明、架构、最新进展、重要决策。没有配置时使用 `README.md`、`docs/ARCHITECTURE.md`、`docs/STATUS.md`、`docs/DECISIONS.md`，已有等价文档则沿用。
3. 配置中的分支和远端是待核对的期望值；实际 Git 状态和用户要求也要核对。冲突时报告，不能按旧进展文档直接切分支。
4. 代码、Git 历史、验证结果与文档不一致时先核实。将已实现、已验证、尚未验证、计划完成分开，避免把计划写成事实。

## 交接约束

- 保留用户现有工作和项目惯例。不要覆盖已有规则或架构文档；初始化可重复执行，合并受管理片段而不重复追加。
- 先核对 Git 仓库、远端、分支、工作区、暂存区和待推送提交，再做相应操作。禁止通过丢弃修改、自动 stash、重置、强推或自动改写历史来“修好同步”。有冲突、分叉或目标不明时保留成果，完成不依赖阻塞的部分并说明处理选项。
- 提交前审查实际变更及未跟踪文件。仅纳入明确属于本次交接的内容；不使用未经审查的全量暂存，也不夹带用户已暂存但与任务无关的修改。密钥、真实环境文件、凭据和业务数据不进入交接提交。
- 进展记录保持可接手：目标、完成情况、验证证据、进行中的位置、已知问题、下一步和环境缺项。重要决策记录原因及影响；文档中不复制整段聊天或敏感日志。
- 同步是显式触发的工作流，不承诺后台运行、跨机共享聊天、自动安装技能或凭据。拉取更新后重新读取规则文件；必要时提示新开会话，使新规则完整生效。
- 网络、身份认证或权限阻塞时保留本地结果并如实报告。不要让用户把密码或令牌贴到聊天，不将本机凭据复制到另一个电脑。

## 完成回报

简短说明：**本地分支和提交、远端核验结果、代码检查结果、环境是否就绪、下一步、仍只在本机的内容**。
未验证远端、未运行测试、配置不全等情况直接写明；文档更新、提交成功、推送成功是三个不同结果。
