# 开工与收工同步

## 共同预检

在项目根目录读取实际 Git 状态：仓库路径、当前分支、upstream、远端 URL、工作区和暂存区、未跟踪文件、最近提交。检测是否处于合并、变基、cherry-pick 或冲突处理中。命令参数使用核实过的实际值并正确引用；以下名称是占位说明，不是可以原样执行的参数。

可使用 `git status --porcelain=v1 --branch`、`git branch -vv`、`git remote -v`、`git log` 和针对文件的 diff。远端地址中的凭据不要出现在回报或文档里。

不在 Git 仓库、detached HEAD、交接目标不明、操作未完成、配置与实际分支冲突时，先处理或说明阻塞。不要使用 main 代替用户真正工作的分支。多 remote、无 upstream 时结合已核实配置选择；无法确定才问用户。

## 开工同步

1. **检查本机工作。** 发现未提交修改、暂存项或未跟踪文件时先检查和保留。为使跨机流程可预测，默认不在脏工作区执行拉取、不自动 stash 或提交；可先 fetch 和只读核对，说明如何处理。显式授权处理后再继续。
2. **获取远端。** 对核实过的交接 remote 执行 fetch。失败则本地内容仍可读取，但必须标明不是已同步的最新状态；不依据旧进展文档宣称接手成功。
3. **比较分支。** 检查远端分支存在，并比较本地 HEAD 与远端分支。相同则无需更新；本地仅落后且工作区干净时使用 `git merge --ff-only` 对核实过的远端跟踪分支快进。仅本地领先时保留本地提交并报告未上传，不自动回退；双方分叉时暂停更新，给出提交摘要及处理选项。不会自动合并或变基。
4. **重新加载上下文。** 更新后再读实际适用的 `AGENTS.md`、配置及交接文档，并核对最近代码差异与 STATUS 所述。进展文档过时、分支不匹配或与代码冲突时注明，按代码和证据核实后修订已授权的文档；必要时提醒新开会话。
5. **检查环境。** 依照真实 README 和配置核对运行时、锁文件、依赖、环境变量、服务和迁移。先检测，按用户已授权的开发范围准备依赖；数据迁移先核实目标数据库及影响，不因“开工”就修改生产数据。缺少密钥时列出变量名和配置方法，不读出秘密。
6. **给出接手摘要。** 报告同步后的分支和提交、上次完成项、未完成项、验证程度、环境缺项、建议下一步。如果用户同时指定了开发任务且条件满足，继续完成该任务；仅开工同步时到摘要为止。

开工成功标准：工作树已与核实过的远端分支对齐，更新后的规则和交接资料已读。环境缺项单独报告；本地领先、分叉、网络失败、脏工作区都不能报告为完整同步成功。

## 收工同步

1. **核实交接范围。** 检查完整工作区、暂存项、未跟踪文件和此前未推送的提交。当前项目本次任务相关的代码、规则和文档都应纳入交接；无法确定的内容保留并报告，必要时问范围，不擅自丢弃或上传。暂存区有无关内容时不得直接一并提交或擅自取消暂存，可在清楚保留原暂存状态的前提下隔离提交，否则说明阻塞。
2. **检查远端关系。** fetch 后比较目标分支。仅本地领先或双方相同时可继续。远端领先或双方分叉时，先核实并保留本地工作，报告同步阻塞；可以继续检查并更新本地交接文档，但不以强推或自动改写历史解决。远端分支尚不存在时，只在已有明确交接目标的情况下首次推送建立该分支。推送权限不等于部署或合并权限。
3. **执行相关检查。** 使用项目约定且适合本次变更的检查，记录实际命令、结果及未运行原因。失败时保留证据。若用户要求修复且能在本次范围内完成则修复；否则用 WIP 状态交接并明确失败。项目强制检查或分支保护优先，不绕过。不要为文档小改增加无意义测试。
4. **更新交接资料。** STATUS 记录用户时区日期和本分支、已完成与已验证内容、进行中的文件或模块、已知问题、下一步、环境缺项。架构、启动方式、重要决策确实变化时更新对应文件。使用实际验证证据，不把“未测”写成“通过”。STATUS 保持当前快照，只有太长时才归档历史。
5. **审查并提交。** 检查最终 diff 和每个将上传的文件；代码、相应文档与必要的新增文件一起提交。使用明确文件范围暂存并再次审查 staged diff；不把忽略文件、密钥或大体积本地数据强行加入。无需变更则不制造空提交，仍核对既有未推送提交。提交身份缺失时使用用户明确指定或当前已验证账号的正确身份，仅在本仓库设置；不要猜邮箱或修改全局配置。
6. **推送并验证。** 将当前核实过的分支显式推送到指定 remote/branch；没有 upstream 时经核实建立。普通推送被拒绝时重新 fetch 一次并说明原因，不强推、不无限重试。使用 `git ls-remote` 核对 `refs/heads/目标分支` 的提交号与本地 HEAD 相同，并检查本地 upstream 状态；若使用已授权的 GitHub 接口则核对同一分支的提交号。单看 push 日志或 fetch 之前的 upstream 状态不足以宣称远端一致。
7. **最终回报。** 分别报告“文档已更新／本地已提交／远端已核验”，提供分支、提交、检查结果、下一步以及仍在本机的内容。有遗漏则标记部分交接，不说全部同步。push 后有新改动时再次检查，明确哪些内容不在刚才的提交内。

不要把尚未产生的最终提交号写进将参与该提交的 STATUS，避免反复补提交。交接提交号在最终回报中给出，由 Git 日志查询。验证基于哪一版代码可在 STATUS 写“本次随文档一同提交的代码”，或记录已有基准提交并说明其后改动。

## 异常时保持可恢复

- 无网络或认证失效：在可行范围内完成本地文档和提交，明确远端未同步；给出恢复连接后的待办。
- 分叉、冲突：保留现场，列出本地与远端变化；只有用户已明确授权处理方式时才执行相应处理。
- 文档缺失：先读现有等价资料，按 setup 流程补齐已授权的部分，不因模板缺失重建整个项目。
- 只能通过网页上传：必须保留目录结构，并核对目标分支和提交。不能验证整个交接提交时报告限制；不把上传 ZIP 当成业务项目代码完整同步。
- GitHub 合并请求、部署、权限变更：不属于普通开工／收工自动步骤，按用户另行要求处理。
